Implicit Calls and Shared Names, Not Reflection}

\author{\IEEEauthorblockN{Adarsha S P, Sankalp Shankar, Surabhi Singh, Pravith S Upadhyaya, Abhishek Kumar}

\begin{abstract}
Python call-graph generators are evaluated mostly on micro-benchmarks. We run PyCG and a Pyright-based extractor
on \nStaticAttempted{} pip-installable GitHub repositories and, where the tests could be traced,
score them and three open-weight LLMs against the calls the tests make between the project's own
functions. PyCG failed on \pctPycgFailRun{} of the \nPycgRun{} repositories it was run
on\sweepAbstract{} On \nRuntimeRepos{} traced repositories, the union of both analysers finds a
median of \edgeUnionMed{} of observed calls (\poolRecallUnion{} pooled). Of the calls it misses,
\missUnnamedAll{} reach functions the caller never names (special methods, library callbacks) and
\missSharedAll{} go through shared method names; reflection accounts for \pctMissReflective.
Pyright beats PyCG in \nPyrightBeatsPycg{} of \nRuntimeRepos{} repositories. LLM
resolvers\rqFourAbstract{} We will release the corpus, pipelines and measurements.
\end{abstract}

\section{Introduction}

A call graph records which functions call which. Tools for program comprehension, refactoring,
dead-code detection and vulnerability reachability are built on one, and code-graph retrieval
for LLM agents now uses it to decide which code a model sees~\cite{ouyang2024repograph}. Python
makes call graphs hard to build statically: dispatch depends on runtime types, functions are
passed around as values, and decorators, properties and registries hide calls behind syntax that
does not look like a call.

PyCG~\cite{salis2021pycg} is the standard Python call-graph generator and the baseline in recent
benchmarks~\cite{bouzenia2024dypybench} and in studies of LLMs as static
analysers~\cite{venkatesh2025llmcg}. Its accuracy, like that of its successors~\cite{huang2023jarvis},
is mostly reported on hand-written micro-benchmarks, where every call has a known answer. Real
repositories are larger, messier and have no answer key. For Java, executing programs to bound
the recall of static call graphs is established practice~\cite{sui2020recall,helm2024totalrecall};
for Python, DyPyBench compared PyCG with dynamic call graphs on 50 projects and found only 49\% of
the dynamic edges in PyCG's output~\cite{bouzenia2024dypybench}, but attributed 59\% of the missing callees to
methods of built-in types and about 12\% to naming differences, rather than to analysis gaps.
We exclude built-in calls by construction and map every tool onto one node set
(Section~\ref{sec:nodes}).

This paper asks what static analysers miss on real Python code once those artifacts are removed,
whether the standard tool is a stable instrument, and whether LLMs recover the misses. Our numbers
are not a correction of DyPyBench's: the corpus, the tracer and the edge definition all differ.
We ask four questions.
\textbf{RQ1 (reliability):} Does a widely used analyser produce a call graph at all, and the same
one twice? \textbf{RQ2 (agreement):} How much do two static analysers agree on the same code?
\textbf{RQ3 (recall):} Of the calls a project's tests make, how many do static analysers find, and
where do they miss? \textbf{RQ4 (LLMs):} Can LLMs resolve the calls static analysis misses, and at
what cost in false claims?

\noindent Our findings and contributions are:
\begin{enumerate}
\item \textbf{PyCG is not a fixed instrument.} The baseline of recent Python call-graph studies
fails on \pctPycgFailRun{} of the repositories it was run on (timeouts, crashes, out of memory),
and on the timed-out
repositories we probed its fixpoint diverges. Where it finishes, the size of its raw output changes
with \texttt{PYTHONHASHSEED} on \pctNondet{} of repositories\sweepContribution{}
\item \textbf{Implicit calls and shared names, not reflection.} With calls into built-in types excluded
and every tool mapped onto one node set, the union of two static analysers still misses a median
of \edgeUnionMissMed{} of observed calls per repository. Of all the calls it misses,
\missUnnamedAll{} reach a function the caller never names (special methods, library callbacks) and
\missSharedAll{} go through method names shared by several functions. Functions that use reflection
account for \pctMissReflective{} of misses, and a dynamism score built on reflective and dynamic
constructs shows no clear relation to recall ($\rho = \densitySpearman$, $p = \densitySpearmanP$).
\item \textbf{Pyright beats PyCG as a call resolver.} Pyright finds more observed calls than
PyCG in \nPyrightBeatsPycg{} of \nRuntimeRepos{} repositories (median per-repository gain \pyrMinusPycgMed, 95\% CI
\ciPyrMinusPycgMed), at similar precision (\itemPyrightP{} against \itemPycgP{}), and on \mapPyrWinsLenient{} of
\nMapRepos{} when PyCG's names are mapped leniently.
\item \textbf{LLMs reverse the micro-benchmark verdict on recall, not on precision.} Asked which of
the names on a caller's executed lines it called, LLMs find more observed calls than static
analysis (\llmQwenR--\llmOneTwentyR{} against \llmTwentyStaticR{}) but claim calls the tests never
made. A static-plus-LLM combiner trained on other projects gives a small F1 gain on unseen
repositories, from \loroUnionFone{} to \loroCombFone{} (paired 95\% CI of the gain \ciLoroDiffUnion), about as much as a plain union of Pyright and
the best LLM.
\item \textbf{A pinned corpus and pipeline}, to be released: discovery, dynamism scoring, automated
build triage with recorded image digests and dependency locks, traces and every measurement.
\end{enumerate}

\section{Related Work}

\textbf{Python call graphs.} PyCG~\cite{salis2021pycg} computes an assignment graph over
modules with a fixpoint and reports high precision and moderate recall on its micro-benchmark.
Jarvis~\cite{huang2023jarvis} adds flow sensitivity and reports higher precision, recall and speed
than PyCG. Both evaluate primarily on micro-benchmarks and a handful of applications. We use
PyCG because it remains the most common baseline, and we report its failure modes at scale.

\textbf{Static versus dynamic call graphs.} Sui et al.~\cite{sui2020recall} and Helm et
al.~\cite{helm2024totalrecall} execute Java programs to bound the recall of static call graphs
and attribute misses to language features; Reif et al.~\cite{reif2019judge} test which unsound
features each Java framework handles. DyPyBench~\cite{bouzenia2024dypybench} provides 50
executable Python projects and compares PyCG to dynamic call graphs recorded with
DynaPyt~\cite{eghbali2022dynapyt}.

\textbf{Non-determinism in static analysers.} Miao et al.~\cite{miao2025nondet} study
non-deterministic behaviour in twelve static analysers, PyCG among them, and trace most of it to
concurrency, analysis bugs and assumed orderings of unordered data structures. We measure how
often hash-seed order changes PyCG's call graph across a corpus, and what it does to recall.

\textbf{LLMs as static analysers.} Venkatesh et al.~\cite{venkatesh2025llmcg} evaluate 24 LLMs on
call-graph and type-inference micro-benchmarks and find PyCG ahead of every LLM on call graphs.
We revisit the question on real code with execution-derived labels. Table~\ref{tab:compare}
sets this study against the two closest Python studies.

\section{Study Design}

\subsection{Corpus}

We searched GitHub for Python repositories with at least 50 stars, a push after August 2023, a
\texttt{pyproject.toml} or \texttt{setup.py}, and a test suite. From the \nPoolMatched{} matches we drew
a seeded random sample (not ranked by stars), froze each repository's commit on the day of
discovery, and scored its source with an AST-based dynamism score: weighted counts of dynamic
constructs (\texttt{getattr} with a non-literal name, dynamic imports, \texttt{eval}/\texttt{exec},
registries, decorators) per thousand lines, with thresholds calibrated on a \nRefSet-repository
reference set (LOW below \thrLowMed, HIGH from \thrMedHigh). Repositories were binned LOW, MED or HIGH and interleaved into a \nQueued-repository
queue, so that stopping early still leaves balanced strata.

An automated triage worked the first \nTriaged{} repositories of the queue. Each was installed
into a pinned \texttt{python:3.12} image (recorded by digest), falling back to 3.11 and 3.10 on
interpreter or dependency errors, and its tests were collected with \texttt{pytest}. Every
attempt records the resolved commit, the image digest and a hash of the frozen dependency list.
Of these, \nAdmissible{} built and collected at least one test, \nCollectEmpty{} built but
collected none, and the rest did not build. The \nStaticAttempted{} of the \nAdmissible{} whose
licence permits redistribution entered static extraction.

\subsection{Nodes and edges}\label{sec:nodes}

Both analysers are mapped onto one node set, inventoried from the AST: modules, classes'
bodies, functions, methods and lambdas, identified by file path and qualified name (line numbers
are not part of identity). Comprehensions fold into their enclosing function; a method call
resolves to the defining class in the method resolution order. An edge is \emph{in-universe}
when both caller and callee are callables of the repository itself; calls into builtins, the
standard library and third-party packages are excluded, because no call-graph tool claims to
model them and including them would inflate every miss rate. Because both analysers and the
tracer are mapped onto the same node identities, naming differences between tools, which
DyPyBench reports~\cite{bouzenia2024dypybench}, can enter only as mapping losses (Section~\ref{sec:threats}).

\subsection{Static analysers}\label{sec:static}

\textbf{PyCG} 0.0.8 runs three times per repository, with \texttt{PYTHONHASHSEED} set to 0, 1
and 42. Each run uses its own container, an 8\,GB memory cap and a 1800\,s timeout, with the
repository mounted read-only at the same fixed path, so the hash seed is the only input that
changes between runs. The PyCG graph of a repository is the union of the seeds that finished.

\textbf{Pyright} 1.1.411~\cite{pyright} has no batch call-graph mode. For every call site in the
AST we ask \texttt{pyright-langserver} for the definition of the callee identifier and map the
answer back to a node, so it reports only edges written as calls: a name used without call syntax,
such as a property read, is outside its reach. It runs without the repository's dependencies
installed. Below, \emph{Pyright} means this extractor.

\subsection{Runtime ground truth}

For RQ3 and RQ4 we drew repositories from the \nStaticOk{} where both analysers finished, in two
rounds whose rules were written down before either round was traced. The first round took \nRoundOne{}
repositories (\roundOneStrata) admitted on Python 3.12 with at least 50 tests, a single top-level
package, no heavy native stack and no external service. The second took the \nRoundTwo{} remaining
repositories with at least 20 tests and a single package, allowing native stacks, except two that
need root or a live service. Of these, \nRuntimeExcluded{} could not be traced (Section~\ref{sec:rq3}).
Where PyCG is seed-dependent, its graph here is the union of the three seeds of Section~\ref{sec:static}. Each
repository's own test suite runs under a tracer built on Python 3.12's
\texttt{sys.monitoring}~\cite{pep669}. It records every call between callables of the package,
with the line it came from; calls from test code are attributed to a synthetic entry node, and a
call that passes through library code (a callback handed to the standard library) is charged to
the nearest package frame. We call these \emph{observed calls}: they cover what one run of the tests executes and nothing
else.

\subsection{Call-resolution items}

An \emph{item} is a pair (caller, candidate) in which the candidate's name appears on a line of
the caller that executed under the tests: as a call, as a bare reference (a property read, a
function passed on) or as a class name (reaching its constructor). The label is whether the runtime call graph contains the edge caller$\to$candidate: a property
read counts through the getter it invokes, a class name through its \texttt{\_\_init\_\_}, and a
bare reference only if a frame of this caller, or a library frame it called, made the call. Static
tools are scored by the same edge test. For a uniquely named candidate on a line that executed, an
unobserved claim is strong evidence of a false claim; for a shared name it is weaker, since
another run could dispatch to it, so we report precision separately for the two. A resolver answers yes or no for each item: \emph{name match} (every candidate is a
call, as a text search would assume), PyCG, Pyright, their union, and the LLMs. Calls whose
target never appears by name in the caller cannot be items; they are counted separately so they
do not disappear from anyone's recall.

\subsection{LLM resolvers and a combiner}

We query gpt-oss-20b, gpt-oss-120b and qwen3.8-27b, open-weight models served by Groq, at
temperature 0. Each prompt shows the caller's whole function body (its own lines, without
nested definitions), the definitions of its candidates and the class hierarchy among them, and a
JSON schema restricts the answer to candidate identifiers. The candidate list holds only names on
lines that executed, the same filter that defines items; the models never see static analysis
output. Requests use temperature 0, seed 0 and reasoning effort \emph{low}; each answer records the
requested model ID, token usage and the raw response. Because of API rate limits, the LLMs answer a seeded sample of callers
that contain at least one hard item (a name shared by several functions, a bare reference, or a
pair the static analysers get wrong); every resolver is scored on the same sample.
\rqFourSampleNote{}

A logistic-regression combiner uses ten features: each static analyser's and each LLM's answer,
how the name is written (call, reference, class name), whether it is shared by several
functions, and whether the candidate is a method of the caller's own class. There is no preprocessing or
feature selection, and the hyperparameters (L2 penalty 0.5, 3000 epochs, learning rate 0.3) were
fixed while developing on \texttt{click} and \texttt{toolz}, before any corpus repository was
traced. It is scored out-of-fold, \rqFourCvNote{} Leave-one-repository-out is the primary result.

\section{Results}

\subsection{RQ1: Reliability of PyCG}

Pyright finished every repository whose
package layout was detected. Of the \nPycgRun{} repositories whose layout was
detected, PyCG failed on \nPycgFail{} (\pctPycgFailRun): \nFailTimeout{} hit the 1800\,s timeout on every seed,
\nFailCrash{} crashed on every seed (an \texttt{IndexError} while reading default arguments, or an
\texttt{AttributeError}, both inside PyCG), \nFailOom{} exhausted 8\,GB, and on \nFailMixed{} the
failure mode itself changed with the seed (a timeout on one seed, a crash or out-of-memory on
another). Counted per run, \pctPycgSeedRunsFailed{} of (repository, seed) runs failed, and
\nPycgAnySeedFail{} repositories failed on at least one seed. When PyCG finishes it is fast (median \pycgMedSec{}\,s per run, maximum
\pycgMaxSec{}\,s, well inside the budget). Size is part of the
explanation, since failed repositories are larger (median \medNodesFail{} callable nodes against
\medNodesOk{}), but not all of it: \texttt{\minNodesFailRepo}, with \minNodesFail{} callable
nodes, timed out on every seed. The failure rate matches DyPyBench, where PyCG produced a call
graph for 39 of 50 projects~\cite{bouzenia2024dypybench}.

On \nNondet{} of the \nStaticOk{} repositories where PyCG finished (\pctNondet{}), its raw output
differed in size between the three seeds. For the raw output this count-based check is a lower bound:
two runs can return different edges in equal numbers. Because the counts of unique edges differ, output order or
serialisation cannot explain it, and repository path, image and tool version were identical
across runs, so the seed is the only input that differed. Seeds 0
and 1 ran on both of our hosts: termination agreed, hangs included, in \nRepeatSeedAgree{} of
\nRepeatSeedRuns{} runs; on the \nRepeatNondetRepos{} seed-dependent repositories the same seed
produced the same output size in \nRepeatNondetEqual{} of \nRepeatNondetRuns{} runs, and on the
\nRepeatEdgeIdentical{} seed-independent ones identical edge sets. The spread, $(\max-\min)/\max$ of the raw edge counts, is usually small (median \medSpread{}) but
has a long tail: \nSpreadTen{} repositories vary by 10\% or more, and on \texttt{\maxSpreadRepo}
the edge count varies by \maxSpread{} between seeds. It occurs in every stratum. A tool built on PyCG
pins the seed, noting that it shifts PyCG's fixpoint~\cite{codeanalyzer2025seed}, and Miao et al. include PyCG in a study of
non-deterministic analysers~\cite{miao2025nondet}; how often the seed changes its call graph on real
repositories, and by how much recall, had not been measured.

\textbf{Mechanism.} PyCG computes its graph with a fixpoint whose passes walk hash-ordered sets,
and runs it with no iteration cap; set iteration order depends on \texttt{PYTHONHASHSEED}, which is
random per process unless pinned. The seed therefore changes which fixpoint is reached, not only
the order of the output. \sweepSetLevel{}

\textbf{Two probed timeouts do not converge.} Replaying PyCG's own loop on \texttt{chevron}
(\minNodesFail{} callable nodes) with an iteration cap and a log per pass, its abstract state grew
by \chevGrowth{} definitions on every pass, from \chevDefsFirst{} to \chevDefsLast{} over \chevPasses{}
passes, without converging or revisiting a state: each pass adds definitions under a freshly
numbered lambda (\texttt{render.<lambda192>} by pass~50), so the convergence check can never
succeed. On \texttt{muscriptor} the state exploded instead: the names it tracks grew from
\muscNamesFirst{} to \muscNamesLast{} in \muscPasses{} passes as attributes accumulated on imported
names, and the last pass alone took \muscLastPassMin{} minutes. We did not probe the other
timeouts. Termination itself can depend on the seed: in the three-seed run the failure mode changed with
the seed on \nFailMixed{} repositories\mixedTerminationSentence{}

\subsection{RQ2: Agreement between static analysers}

On the \nStaticOk{} repositories where both finished, the Jaccard similarity of the two
analysers' in-universe edge sets has a median of \jacMed{} (interquartile range
\jacQone--\jacQthree); \nJacBelowHalf{} repositories fall below 0.5 and \nJacAboveEight{} reach
0.8 or more. Of the \nEdgesUnion{} edges found by either tool, \pycgOnlyShare{} are found only by
PyCG and \pyrightOnlyShare{} only by Pyright. Two analysers reading identical source
disagree on roughly a third of the call graph; deciding which is right needs the runtime labels of RQ3.

\section{Discussion}

\textbf{Use a type checker as the baseline.} Pyright alone holds nearly all of the union (median
recall \edgePyrightMed{} against \edgeUnionMed)\ifdefined\sweepUnionMaxDelta, and adding it damps
PyCG's seed effect on recall to at most \sweepUnionMaxDelta\fi. Tools that consume call graphs
should start from a type checker, not from PyCG; studies that keep PyCG should pin and report
\texttt{PYTHONHASHSEED} or report the spread over several seeds.

\section{Threats to Validity}\label{sec:threats}

\textbf{Ground truth is workload-conditional.} The tracer sees only what the test suites execute.
Recall is measured against the calls the tests made, a subset of the calls the program can make,
and precision only on lines that executed; a static edge that no test exercised is neither
confirmed nor counted against the tool.

\textbf{Environments.} Runtime traces (RQ3, RQ4) were collected on a second x86-64 host, installing
each repository by the triage recipe rather than from its frozen dependency list, so dependency
versions may differ; the static graphs are computed from source and are unaffected. \texttt{click}
and \texttt{toolz} were traced on an arm64 machine; both are pure Python.

\textbf{Choice of analysers.} PyCG is archived but still the baseline in 2024--25
studies~\cite{bouzenia2024dypybench,venkatesh2025llmcg}, so its seed dependence bears on their
numbers. Measuring Jarvis~\cite{huang2023jarvis} on the same traces is future work.

\textbf{Tool versions and configuration.} We measure one version of each analyser. PyCG's 30-minute budget is a choice; on the two timed-out repositories we probed, the fixpoint
did not converge, but we did not probe all \nFailTimeout{}.

\textbf{LLM sample and serving.} The LLMs answered a sample of callers enriched for hard items, so
their scores are not comparable to static scores on all items. One enrichment criterion, a pair the static analysers get wrong,
lowers static recall on the sample by construction; without the callers it alone admitted, the
results barely change (Section~\ref{sec:rq4}). The candidate list comes from executed lines,
so the LLMs choose among names the tests reached rather than build a graph, which flatters them
relative to a deployed tool. The corpus is public and may be in the
models' training data. Each model answered once; we record the requested model, but not
the serving model. The combiner's hyperparameters were fixed on \texttt{click} and \texttt{toolz},
which are also evaluated; without them its gain holds (Section~\ref{sec:rq4}).

\textbf{Mapping.} PyCG's names are mapped onto our node set strictly. Rerun on the \nMapRepos{}
traced corpus repositories and remapped leniently (a class to its \texttt{\_\_init\_\_}, a subclass
method to the base that defines it, a unique name suffix), its median recall rises from
\mapMedStrict{} to \mapMedLenient{} and its constructor recall from \mapCtorStrict{} to
\mapCtorLenient; \pctMapLoss{} of the calls Pyright finds and strict PyCG misses are mapping losses.
Pyright still finds more on \mapPyrWinsLenient{} of \nMapRepos{} repositories, and the union is
unchanged (+\mapUnionPoolDelta{} pooled).

\textbf{Corpus.} The corpus excludes repositories that cannot be installed from their root with
\texttt{pip} or that collect no tests, which biases it against applications and monorepos. The
runtime subset favours small, pure-Python packages whose test suites need no external services.
The LOW stratum of the runtime subset is the thinnest, with \nLowRuntime{} repositories.

\section{Conclusion}

On pip-installable, tested Python repositories, the standard static call-graph generator fails on
a fifth of the corpus, its call graph depends on the hash seed on \nSetNondet{} of the \nSetSwept{}
it finished, and two static analysers disagree on a third of the edges. Measured against the calls tests actually make, \rqConclusion{}
Corpus pins, image digests, pipelines and all
results will be released upon publication.
